# 项目过程记录：遇到的问题、改动和实验结论

更新日期：2026-10-11。本文记录已经实际完成的工作；计划中的改进单独列在文末。数字以各 JSON 报告为准。Git 分支用于保留不同方案；GitHub 默认分支现为 `word_token_branch`，但网页仍使用原字符模型。

## 1. 选题与目标

课程项目选择“中文短文本情感识别”：用户在网页现场输入一句中文，系统输出偏正向或偏负向；同时使用十万级数据完成清洗、统计、训练和效果评价。项目把“模型是否依赖表情、能否理解否定词”作为重点分析问题。当前只做二分类，没有中性类别；网页给出的决策分数不是正确概率。

## 2. 数据获取、清洗和划分

- 使用 `weibo_senti_100k` 的第三方镜像。原始 119,988 条；文件哈希、来源和版本记录在 `README.md` 与 `reports/data_audit.json`。原始作者、标注过程及再分发许可未完全确认，原始语料不提交到 Git。
- 第一轮清洗统一文本格式，删除同一规范化文本出现正负标签冲突的整组记录及同标签重复记录，保留 116,918 条。这里的“冲突”不等于已经证明标注错误。
- 为避免近乎相同的正文同时进入训练和测试，按去掉链接、@提及、方括号表情等内容后的正文指纹分组。排除正文指纹不足 4 字符的 6,269 条后，固定划分 110,649 条：训练 88,814、验证 10,908、测试 10,927。三组正文指纹交集为 0；具体规则及局限见 `reports/stage2_notes.md`、`reports/split_report.json`。
- 抽查训练数据时发现转发链、混合情感、疑似编码噪声，以及正文接近中性但带明显表情的记录。抽查不是重新标注；未据此修改标签。

## 3. 环境与 Spark：能做什么、没做成什么

本机使用 Windows 11、Python 3.12、Java 21、PySpark 4.0.1。工作目录含中文，Spark 启动时遇到路径编码问题；`start_spark.ps1` 通过临时短路径运行。PySpark DataFrame 已读取 88,814 条训练记录，完成正则清洗、长度计算和按标签统计，结果在 `reports/spark_data_analysis.json`。训练数据的正负两类记录**全部含方括号表情**，提示模型可能利用表情这一强线索。

曾尝试用 Spark MLlib 训练完整情感模型，但此 Windows 环境的 Hadoop 缺少 `winutils.exe`，无法写入训练临时文件。`reports/environment.json` 中的 Spark 小样例训练只是环境检查。因此正式情感分类模型由 scikit-learn 训练，不能称作 Spark 模型；Spark 贡献是十万级数据处理与统计。没有进行多机分布式实验。

## 4. 初版基线：字符 1—2 字片段

`scripts/train_baseline.py` 把文本转换为字符 1—2 元 TF-IDF 特征，对比朴素贝叶斯与 SGD 训练的逻辑回归，并分别比较保留／去掉表情。向量器只在训练集 `fit`；验证集用于选方案，测试集用于最终评价。面向现场自由输入，优先从去表情模型中选择，最终选中逻辑回归。

| 方案 | 验证集准确率 |
| --- | ---: |
| 去表情 + 朴素贝叶斯 | 75.26% |
| 去表情 + 逻辑回归 | **77.66%** |
| 保留表情 + 朴素贝叶斯 | 90.23% |
| 保留表情 + 逻辑回归 | 98.99% |

去表情模型在独立测试集准确率为 **77.29%**，详见 `reports/baseline_results.json`。保留表情的高分说明表情与标签高度相关，不能证明模型充分理解正文；目前也没有证据证实标签由表情自动生成。

固定人工诊断句暴露出问题：“今天不开心。”被误判为正向；中性句也被强制二选一。字符片段和线性分类器能学习常见组合，却没有明确的“否定词作用于后面的情感词”的机制。诊断句不计入正式准确率。

## 5. 现场演示与仓库使用

`app.py` 提供本机浏览器输入／输出；`models/baseline.joblib` 保存向量器与分类器，无需现场重新训练。为让同学不用 VS Code 也能使用，增加 Windows 双击脚本 `start_demo.bat`：在安装 Python 3.12 的电脑上创建环境、首次联网安装演示依赖并打开浏览器。页面只绑定 `127.0.0.1`，所以每台电脑要各自运行；这不是公共在线服务。

初期 Git 仓库包含整个作业目录，后来调整为只以 `sentiment_project` 为仓库根目录。已建立 `main`、`4_character_branch` 和 `word_token_branch`，保留不同实验。曾出现“浏览器能打开 GitHub，但 VS Code 推送超时”：系统浏览器使用本机 `127.0.0.1:7897` 代理，Git 当时没有配置代理；给仓库配置相同代理后推送成功。GitHub 仓库改名后，远程地址更新为 `TheGreatPeter122/sentiment_project`。这些是版本管理／网络问题，与模型效果无关。

## 6. 扩大字符范围：1—4 字实验

在 `4_character_branch` 将 `ngram_range` 从 `(1, 2)` 改成 `(1, 4)`，保持原数据划分和训练流程。训练约 65 秒，结果如下：

| 指标 | 1—2 字基线 | 1—4 字实验 |
| --- | ---: | ---: |
| 验证集准确率 | 77.66% | 77.27% |
| 原测试集准确率 | 77.29% | 77.02% |
| 固定诊断句正确数 | 11/12 | 10/12 |

“今天不开心。”仍被判为正向，决策分数从 `0.269` 降至 `0.122`，但没有越过分类边界；还有一条转折句由正确变为错误。扩大特征窗口并没有构成有效改进。该实验复用了已经看过的测试集，因此后续不应继续靠反复查看这个测试集来调参。1—4 字分支未替换网页默认模型。

## 7. 中文分词实验

在 `word_token_branch` 增加 `jieba==0.42.1`，分别训练“词及相邻词 TF-IDF”和“字符 1—2 字 + 词及相邻词”组合特征，分类器仍为 SGD 逻辑回归；训练代码为 `scripts/train_word_baseline.py`，结果在 `reports/word_baseline_results.json`。两种实验模型单独保存在 `models/word_baseline.joblib`、`models/hybrid_baseline.joblib`，没有覆盖网页的 `models/baseline.joblib`。该分支只用验证集及固定诊断句比较，没有再次使用测试集选方案。

| 方案 | 验证集准确率 | 固定诊断句正确数 |
| --- | ---: | ---: |
| 原字符 1—2 字模型 | 77.66% | 11/12 |
| 纯词模型 | 76.33% | 10/12 |
| 字符 + 词组合模型 | 77.86% | 11/12 |

纯分词模型未改善整体效果。组合模型比原模型高 **0.20 个百分点**，把“今天不开心。”判对，但另一条否定句判错，专项正确总数没有提高；这点差距不足以证明稳定优势。因此网页没有改为默认使用分词模型。GitHub 默认分支目前已被改成 `word_token_branch`，这是仓库设置，不能解读为组合模型效果已获证实。

首次安装分词库时，项目虚拟环境没有 `pip`；直接运行 `ensurepip` 又因系统临时目录权限失败。将 `TEMP`／`TMP` 指向仓库内被忽略的 `runtime/tmp` 后，成功安装 `pip` 和 `jieba`。其他电脑可以按 `requirements-experiments.txt` 安装实验依赖；演示依赖与分词实验依赖分开，避免双击演示时额外安装分词库。

## 8. 当前结论与下一步

截至本记录，**网页默认仍加载去表情字符 1—2 字模型**；GitHub 默认分支是 `word_token_branch`，其中保留了可复现的分词对比。最可靠的整体测试数字仍是初版独立测试集的 77.29%。分词组合的验证集小幅提升是探索性结果，不能直接当作最终性能提升。

下一步优先建立新的人工核对样本：否定、双重否定、转折、反讽和中性表达各自分组，并准备微博以外的短评用于跨场景测试。先做错误归因和训练数据标签抽查，再考虑有针对性地补充训练样本、比较其他线性分类器或微调中文预训练模型。若要正式宣称新模型优于旧模型，需要使用未被反复用于选方案的新评估数据，并同时报告整体指标和困难句表现。第 9 节记录外部数据准备进展，其余工作尚未完成。

## 9. 增加外部评论数据（2026-10-11）

已从 `SophonPlus/ChineseNlpCorpus` 固定提交下载购物评论 10 类和外卖评论两份原始数据，分别为 62,774 条和 11,987 条。`scripts/fetch_external_data.py` 核对来源文件 SHA256；`scripts/clean_external_data.py` 统一空白和标签字段、去掉无效行、重复与冲突文本，并用与原项目相同的正文指纹排除与现有微博各集合重合的样本。清洗后得到 74,274 条，负向 38,818、正向 35,456。具体删减计数、类别和输出哈希见 `reports/external_data_audit.json`。

新增数据只保存在被 Git 忽略的 `data/raw` 和 `data/processed`，现有模型、训练脚本、数据划分与网页行为均未改变，也未运行训练。前文“补充微博以外的短评作为跨场景测试”中的**数据准备部分已完成**，但外部测试和人工标签核查仍未开展。由于原始标注过程与再分发许可不明，尚不能把这些标签当作已审定的金标准。

## 10. Spark 多来源分析与规模实验（2026-10-11）

新增 `scripts/spark_all_sources.py`，在单机 Spark `local[4]` 模式读取三种来源的 **184,923 条**已清洗记录，统一做正则清洗、文本长度计算，并按来源、标签、商品类别和原有划分分组统计。微博 110,649 条、外部评论 74,274 条，没有把外部评论混入原训练集。外部数据中 20 条文本同时来自购物与外卖源，在报告中单列以避免总数重复。完整统计见 `reports/spark_all_sources.json`；最近一次含 Spark 启动及多次统计的总耗时为 13.47 秒，首次运行约 36.91 秒，说明本机预热和缓存会影响耗时。

另新增 `scripts/benchmark_spark_pipeline.py`，对同一清洗和分组任务分别处理 10,000、50,000、184,923 条，各重复 3 次。先从三种来源确定性地生成不同规模输入文件，再在 Spark JVM 启动后计量 JSONL 读取、正则清洗、长度计算和分组聚合，中位数依次为 0.523、0.555、0.858 秒，见 `reports/spark_scale_benchmark.json`。起初只聚合行数，Spark 优化器跳过了未被使用的清洗列，导致耗时偏低；随后把清洗后长度及表情计数加入聚合并重跑，最终报告仅记录修正后的结果。该实验在一台 Windows 电脑运行，受 JVM 预热和本地文件缓存影响，不能用于声称分布式集群加速。

运行时发现 Windows PowerShell 5 对无 BOM 的中文脚本提示按系统编码解析，导致 `start_spark.ps1` 报语法错误；把启动脚本中的提示文字改为 ASCII 后，可继续使用原命令。Spark 仍提示缺少 `winutils.exe`，但读取与统计成功；没有进行 Spark MLlib 模型训练，也没有改变网页模型。
