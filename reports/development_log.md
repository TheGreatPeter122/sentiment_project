# 项目过程记录：遇到的问题、改动和实验结论

更新日期：2026-10-13。本文按阶段记录已经实际完成的工作。数字以各 JSON 报告为准。网页当前使用第 17 节的四来源统一模型；之前各阶段的网页状态为当时历史记录。

## 1. 选题与目标

课程项目选择“中文短文本情感识别”：用户在网页现场输入一句中文，系统输出偏正向或偏负向；同时使用十万级数据完成清洗、统计、训练和效果评价。项目把“模型是否依赖表情、能否理解否定词”作为重点分析问题。当前只做二分类，没有中性类别；网页给出的决策分数不是正确概率。

## 2. 数据获取、清洗和划分

- 使用 `weibo_senti_100k` 的第三方镜像。原始 119,988 条；文件哈希、来源和版本记录在 `README.md` 与 `reports/data_audit.json`。原始作者、标注过程及再分发许可未完全确认，原始语料不提交到 Git。
- 第一轮清洗统一文本格式，删除同一规范化文本出现正负标签冲突的整组记录及同标签重复记录，保留 116,918 条。这里的“冲突”不等于已经证明标注错误。
- 为避免近乎相同的正文同时进入训练和测试，按去掉链接、@提及、方括号表情等内容后的正文指纹分组。排除正文指纹不足 4 字符的 6,269 条后，固定划分 110,649 条：训练 88,814、验证 10,908、测试 10,927。三组正文指纹交集为 0；具体规则及局限见 `reports/stage2_notes.md`、`reports/split_report.json`。
- 抽查训练数据时发现转发链、混合情感、疑似编码噪声，以及正文接近中性但带明显表情的记录。抽查不是重新标注；未据此修改标签。

## 3. 环境与 Spark：能做什么、没做成什么

本机使用 Windows 11、Python 3.12、Java 21、PySpark 4.0.1。工作目录含中文，Spark 启动时遇到路径编码问题；`start_spark.ps1` 通过临时短路径运行。PySpark DataFrame 已读取 88,814 条训练记录，完成正则清洗、长度计算和按标签统计，结果在 `reports/spark_data_analysis.json`。训练数据的正负两类记录**全部含方括号表情**，提示模型可能利用表情这一强线索。

曾尝试用 Spark MLlib 训练完整情感模型，但此 Windows 环境的 Hadoop 缺少 `winutils.exe`，无法写入训练临时文件。`reports/environment.json` 中的 Spark 小样例训练只是环境检查。因此正式情感分类模型由 scikit-learn 训练，不能称作 Spark 模型；Spark 贡献是十万级数据处理与统计。没有进行多机分布式实验。

## 4. 初版基线：字符 1—2 字片段

`scripts/train_baseline.py` 把文本转换为字符 1—2 元 TF-IDF 特征，对比朴素贝叶斯与 SGD 训练的逻辑回归，并分别比较保留／去掉表情。向量器只在训练集 `fit`；验证集用于选方案，测试集用于最终评价。面向现场自由输入，优先从去表情模型中选择，最终选中逻辑回归。

| 方案 | 验证集准确率 |
| --- | ---: |
| 去表情 + 朴素贝叶斯 | 75.26% |
| 去表情 + 逻辑回归 | **77.66%** |
| 保留表情 + 朴素贝叶斯 | 90.23% |
| 保留表情 + 逻辑回归 | 98.99% |

去表情模型在独立测试集准确率为 **77.29%**，详见 `reports/baseline_results.json`。保留表情的高分说明表情与标签高度相关，不能证明模型充分理解正文；目前也没有证据证实标签由表情自动生成。

固定人工诊断句暴露出问题：“今天不开心。”被误判为正向；中性句也被强制二选一。字符片段和线性分类器能学习常见组合，却没有明确的“否定词作用于后面的情感词”的机制。诊断句不计入正式准确率。

## 5. 现场演示与仓库使用

`app.py` 提供本机浏览器输入／输出；`models/baseline.joblib` 保存向量器与分类器，无需现场重新训练。为让同学不用 VS Code 也能使用，增加 Windows 双击脚本 `start_demo.bat`：在安装 Python 3.12 的电脑上创建环境、首次联网安装演示依赖并打开浏览器。页面只绑定 `127.0.0.1`，所以每台电脑要各自运行；这不是公共在线服务。

初期 Git 仓库包含整个作业目录，后来调整为只以 `sentiment_project` 为仓库根目录。已建立 `main`、`4_character_branch` 和 `word_token_branch`，保留不同实验。曾出现“浏览器能打开 GitHub，但 VS Code 推送超时”：系统浏览器使用本机 `127.0.0.1:7897` 代理，Git 当时没有配置代理；给仓库配置相同代理后推送成功。GitHub 仓库改名后，远程地址更新为 `TheGreatPeter122/sentiment_project`。这些是版本管理／网络问题，与模型效果无关。

## 6. 扩大字符范围：1—4 字实验

在 `4_character_branch` 将 `ngram_range` 从 `(1, 2)` 改成 `(1, 4)`，保持原数据划分和训练流程。训练约 65 秒，结果如下：

| 指标 | 1—2 字基线 | 1—4 字实验 |
| --- | ---: | ---: |
| 验证集准确率 | 77.66% | 77.27% |
| 原测试集准确率 | 77.29% | 77.02% |
| 固定诊断句正确数 | 11/12 | 10/12 |

“今天不开心。”仍被判为正向，决策分数从 `0.269` 降至 `0.122`，但没有越过分类边界；还有一条转折句由正确变为错误。扩大特征窗口并没有构成有效改进。该实验复用了已经看过的测试集，因此后续不应继续靠反复查看这个测试集来调参。1—4 字分支未替换网页默认模型。

## 7. 中文分词实验

在 `word_token_branch` 增加 `jieba==0.42.1`，分别训练“词及相邻词 TF-IDF”和“字符 1—2 字 + 词及相邻词”组合特征，分类器仍为 SGD 逻辑回归；训练代码为 `scripts/train_word_baseline.py`，结果在 `reports/word_baseline_results.json`。两种实验模型单独保存在 `models/word_baseline.joblib`、`models/hybrid_baseline.joblib`，没有覆盖网页的 `models/baseline.joblib`。该分支只用验证集及固定诊断句比较，没有再次使用测试集选方案。

| 方案 | 验证集准确率 | 固定诊断句正确数 |
| --- | ---: | ---: |
| 原字符 1—2 字模型 | 77.66% | 11/12 |
| 纯词模型 | 76.33% | 10/12 |
| 字符 + 词组合模型 | 77.86% | 11/12 |

纯分词模型未改善整体效果。组合模型比原模型高 **0.20 个百分点**，把“今天不开心。”判对，但另一条否定句判错，专项正确总数没有提高；这点差距不足以证明稳定优势。因此网页没有改为默认使用分词模型。当时 GitHub 默认分支曾改为 `word_token_branch`；各实验历史如今已归并到唯一的 `main`，分支设置不能解读为组合模型效果已获证实。

首次安装分词库时，项目虚拟环境没有 `pip`；直接运行 `ensurepip` 又因系统临时目录权限失败。将 `TEMP`／`TMP` 指向仓库内被忽略的 `runtime/tmp` 后，成功安装 `pip` 和 `jieba`。其他电脑可以按 `requirements-experiments.txt` 安装实验依赖；演示依赖与分词实验依赖分开，避免双击演示时额外安装分词库。

## 8. 当前结论与下一步

**2026-10-11 补充：以下是前期计划。结合课程要求，人工标注现已暂缓；最新完成的否定、转折特征实验及数据处理过程见第 11 节。**

截至初版与分词实验阶段，**网页默认仍加载去表情字符 1—2 字模型**；当时 GitHub 默认分支是 `word_token_branch`，其中保留了可复现的分词对比。该阶段最可靠的整体测试数字是初版独立测试集的 77.29%。分词组合的验证集小幅提升是探索性结果，不能直接当作最终性能提升。

下一步优先建立新的人工核对样本：否定、双重否定、转折、反讽和中性表达各自分组，并准备微博以外的短评用于跨场景测试。先做错误归因和训练数据标签抽查，再考虑有针对性地补充训练样本、比较其他线性分类器或微调中文预训练模型。若要正式宣称新模型优于旧模型，需要使用未被反复用于选方案的新评估数据，并同时报告整体指标和困难句表现。第 9 节记录外部数据准备进展，其余工作尚未完成。

## 10. Spark 多来源分析与规模实验（2026-10-11）

新增 `scripts/spark_all_sources.py`，在单机 Spark `local[4]` 模式读取三种来源的 **184,923 条**已清洗记录，统一做正则清洗、文本长度计算，并按来源、标签、商品类别和原有划分分组统计。微博 110,649 条、外部评论 74,274 条，没有把外部评论混入原训练集。外部数据中 20 条文本同时来自购物与外卖源，在报告中单列以避免总数重复。完整统计见 `reports/spark_all_sources.json`；最近一次含 Spark 启动及多次统计的总耗时为 13.47 秒，首次运行约 36.91 秒，说明本机预热和缓存会影响耗时。

另新增 `scripts/benchmark_spark_pipeline.py`，对同一清洗和分组任务分别处理 10,000、50,000、184,923 条，各重复 3 次。先从三种来源确定性地生成不同规模输入文件，再在 Spark JVM 启动后计量 JSONL 读取、正则清洗、长度计算和分组聚合，中位数依次为 0.523、0.555、0.858 秒，见 `reports/spark_scale_benchmark.json`。起初只聚合行数，Spark 优化器跳过了未被使用的清洗列，导致耗时偏低；随后把清洗后长度及表情计数加入聚合并重跑，最终报告仅记录修正后的结果。该实验在一台 Windows 电脑运行，受 JVM 预热和本地文件缓存影响，不能用于声称分布式集群加速。

运行时发现 Windows PowerShell 5 对无 BOM 的中文脚本提示按系统编码解析，导致 `start_spark.ps1` 报语法错误；把启动脚本中的提示文字改为 ASCII 后，可继续使用原命令。Spark 仍提示缺少 `winutils.exe`，但读取与统计成功；没有进行 Spark MLlib 模型训练，也没有改变网页模型。

## 11. 记录数据处理并继续训练否定、转折特征（2026-10-11）

结合《大数据导论》的知识覆盖、技术工作量及模型评价要求，本轮把重点放在“文本处理过程及其效果”。人工补标暂缓，复用原情感标签，采用训练前固定的三组对照：字符基线、加入否定局部特征、再加入转折前后特征。

本机缺少原训练数据，先恢复固定版本的微博 CSV，复用清洗与划分脚本。原始文件以及三个划分的哈希均与历史记录一致。训练 88,814 条、验证 10,908 条；测试只核对哈希，不读取内容或预测。训练和验证原文均保留，新增去表情正文、否定位置、局部片段及转折前后字段，逐条轨迹保存到本地忽略目录。

同轮三组验证准确率分别为 77.6311%、77.5211%、77.6494%；Macro-F1 为 0.776310、0.775058、0.776304。最终增强组相对同轮基线改对 232 条、改错 230 条，仅净增 2 条；转折候选子集净增 13 条。“今天不开心”被改对，但“我一点也不喜欢原神”仍略偏正向，“A/扫码了”也未解决。不能把局部改善写成整体语义理解提升。

现有网页模型验证准确率 77.6586%，与本轮重训略有差别：词表截断时选择的同频词项不同。已核验本轮三组使用相同基础词表和 IDF，因此只在同轮方案间作控制比较。单次运行不能证明稳定提升，原网页模型保持不变。新模型单独保存在 `models/structure_experiments/20261011_125159/`。

完整的阶段数量、环境、规则示例、特征维度、耗时、误判对照、限制和复现命令见 [数据处理过程记录](text_structure_process.md)；机器可读结果见 [text_structure_results.json](text_structure_results.json)。运行编号 `20261011_125159`，总耗时约 27.6 秒。没有进行本轮 Spark 模型训练，也没有扩充人工情感金标准。

## 12. 多来源日常评论优化及规则修订（2026-10-11）

用户确定后续范围为日常评论整体表现、否定和转折，社群黑话暂不讨论，人工标注继续暂缓。训练前固定方案见 [daily_review_protocol.md](daily_review_protocol.md)，完整过程及图表见 [日常评论数据处理记录](daily_review_process.md)。

恢复固定版本的购物和外卖源文件，校验 SHA256 后复用清洗脚本，重建 74,274 条外部清洗记录，输出哈希与历史记录一致。20 条跨来源共有文本隔离，剩余按来源×标签确定性分层划分：训练 59,402、验证 7,423、新保留测试 7,429。外部划分之间以及与原微博各划分的指纹组交集均核对为 0；语义近重复未完全排除。

结合原微博得到混合训练 148,216 条、共同验证 18,331 条。先比较微博单来源、直接混合、来源×标签平衡三组数据组成；选择直接混合后，再比较结构 v1 与修订的 v2。v2 在保留正文及清洗后偏移量的前提下排除“特别、别人、但愿”等词内候选误命中。所有方案用同一 v2 掩码评价否定/转折子集，避免分母变化。

五组均使用相同分类器设置，分别运行三个固定种子。三来源验证 Macro-F1 等权平均的均值从单来源的 0.794160 提升至混合字符基线的 0.858259；结构 v1 为 0.861512，v2 为 0.861781。按预先规定选择 v2，代表种子固定为 20261010。v2 相对 v1 的差距很小，小于本轮种子波动，不能宣称稳定优越。

锁定记录先写入磁盘，再进行新外部保留测试推理：新模型准确率 91.68%、Macro-F1 0.9165；同轮固定种子的微博单来源对照准确率 80.05%。否定候选准确率 79.59%→91.75%，转折候选 69.01%→86.65%。新模型相对对照改对 986 条、改错 122 条。原微博测试集没有重新评价。

代价是微博验证准确率均值从单来源 77.58% 降至新模型 76.79%。最大收益来自加入新来源及训练条数增加，不能将提升全部归因于规则优化。新模型判对“今天不开心”“我一点也不喜欢原神”，但仍误判“这次服务没有让我满意”及一条“虽然包装很漂亮，但东西实在太难用了”的转折句；这些开发诊断不计入正式准确率。

运行编号 `20261011_133237`，完整执行约 94.9 秒。模型及原文轨迹保存在忽略目录，新模型可通过 `scripts/predict_daily_reviews.py` 独立测试；网页原模型未覆盖。训练记录、源划分、权重、特征维度、逐条预测和事件日志均保存。新保留测试已经使用，后续优化应重新设计评价，避免反复依赖它选方案。

## 13. 网页同步新模型（2026-10-11）

按用户要求，将第 12 节锁定的 `structure_v2`、直接混合、代表种子 `20261010` 模型复制为固定演示文件 `models/daily_review.joblib`。复制前核对实验锁定的 SHA256，复制后内容一致；版本记录为 `models/daily_review.json`，保留实验来源路径与运行编号。初版模型仍作为历史基线保留。

网页和命令行统一调用 `daily_review_model.py`，加载时校验模型哈希，由模型自身完成去表情及结构特征转换。网页同步标明微博、购物和外卖训练来源、结构 v2 与非概率分数；双击启动脚本检查新模型及版本文件。演示可脱离本地实验目录运行，后续训练不会自动改变演示版本。

## 14. 公开评论采集试点（2026-10-13）

先使用 GitHub 公开 Issues API 验证采集流程，得到 65 条中文项目反馈标题；标题级初标为 58 条负向、7 条不明确，但由于几乎没有正例且 Issue 本来偏向问题反馈，没有用于模型训练。采集文件与初标 CSV 留在本机忽略目录，爬虫源码和计数报告保留在仓库。

用户提出尝试 B 站评论或弹幕后，核对其用户协议，发现未经书面许可的自动脚本采集受限，因此选择 Steam 官方公开评测 API。新脚本 `scripts/crawl_steam_reviews.py` 分别请求最近简体中文推荐和不推荐评测，顺序访问并留间隔；只保存评测 ID、游戏 ID、清洗后的短文本、创建时间和用户推荐选择衍生的弱标签，不保存作者信息。首次试点请求 4 页，获得 399 条，长度及中文过滤后保留 193 条，其中推荐 62 条、不推荐 131 条；原始评测及清洗后文件不上传，计数、查询条件及 SHA256 见 `reports/steam_review_pilot.json`。短评筛选后类别并不平衡；整篇推荐选择也不等同于逐句情绪。此批数据尚未用于训练、测试或网页预测，下一步应人工抽样检查弱标签及文本质量。

## 15. Steam 多游戏批量采集与续跑（2026-10-13）

用户确认试点初筛后，扩展到五款游戏的简体中文评测。`scripts/crawl_steam_reviews_bulk.py` 分游戏、分推荐选择按游标顺序读取，逐页把清洗后记录、查询游标和计数写入 Git 忽略的本地检查点；重复执行会跳过已有页面。采集中发现某页只返回 99 条却仍有后续游标，于是将停止条件改为“空页或游标不前进”，补抓之前漏掉的页面。另一次 TLS 连接异常后，从检查点续跑，并加入只针对临时网络错误的有限重试；HTTP 429 不会自动重试。

该阶段 100 页共读取 9,998 条评测。因长度或中文不足排除 4,710 条，标签或语言不符排除 4 条，去重排除 17 条，得到 5,267 条短评：推荐 1,914，不推荐 3,353。当时已核对唯一评测 ID、唯一文本、非空时间和哈希；文本长度中位数 24 字，九成不超过 120 字。此轮从 193 条试点扩大约 27 倍，但尚非十万条 Steam 新数据；随后第 16 节继续扩量，当前 `reports/steam_reviews_bulk.json` 记录的是最终十万级结果。短评筛选和分别请求正负两类会改变自然分布，这些仍是推荐倾向的弱标签，未并入训练、测试或网页模型。

## 16. Steam 十万级扩量（2026-10-13）

用户要求继续扩大到约十万条。保留五款游戏的原检查点，新增 Dota 2、Counter-Strike 2、PUBG、怪物猎人：世界和 GTA V 增强版。原定每款推荐／不推荐各最多 100 页，首轮全局去重后得到 87,476 条；随后沿用检查点把上限提高到 120 页。采集曾按用户要求在第 1,003 页检查点暂停，恢复网络后从下一页续跑，已保存的页面均未重新请求。

Steam 在游标末尾有时返回 `num_reviews=0` 却省略 `reviews` 数组；已将其识别为空页，而不是报结构错误。另一种情况是页面少于 100 条但游标仍前进，因此不能单凭页长结束。脚本仍顺序请求、限制最小间隔，临时网络失败有限重试，HTTP 错误不自动重试。检查点保持在本机 Git 忽略目录。进一步核验发现极少数正文含孤立的 `http://`，已扩充链接遮盖规则，并在重建时对旧检查点再次应用清洗。

最终读取 2,170 页、216,355 条原始评测；长度或中文不足排除 111,684 条，语言／推荐选择不符排除 24 条，剩余 104,647 条通过单页筛选；跨页及跨游戏的 ID／正文阶段再排除 1,745 条，得到 **102,902 条唯一短评**，其中推荐 39,694、不推荐 63,208。十款游戏逐源数量、采集时间范围及输出 SHA256 见 `reports/steam_reviews_bulk.json`。独立核对了文件哈希、唯一 ID、唯一正文、完整时间、十款来源及标签计数；文本长度中位数 22 字，文件约 24 MB。此数量只是 Steam 弱标签短评库，尚未并入现有训练、验证、测试或网页模型，也不能直接作为正式精度结论。

## 17. Steam 数据并入唯一演示模型（2026-10-13）

第 16 节末尾的“尚未并入”是当时状态。之后先训练了一个仅用 Steam 的历史对照模型，留出测试准确率 90.57%；又用单机 Spark 与 Python 对同一 Steam 输入执行清洗和分组统计，全量约十万条的三次中位耗时分别为 0.325 秒和 0.306 秒。100 条按游戏及弱标签平衡抽样的 AI 辅助初审发现 6 条明确文本与推荐选择冲突、17 条混合或不明确；它不是人工金标准。详情见 `steam_training_results.json`、`steam_spark_process.md` 和 `steam_audit_review.md`。

按用户明确的项目目标，Steam 最终不是第二套单独部署的模型，而是用爬虫取得的第四个训练来源。统一训练前发现 Steam 与旧来源以及 Steam 自身划分之间存在正文指纹重合，先隔离这些记录，再用微博 88,814、购物 49,919、外卖 9,483、Steam 81,983 条，共 **230,199 条**训练同一个结构 v2 模型。三个 Steam 权重按四来源等权验证 Macro-F1 选定 1.0；统一模型已取代网页原演示模型。Steam 测试诊断准确率 89.60%，购物＋外卖合计 91.47%；微博验证略有退步。测试集此前已有总体报告，本轮不称首次独立盲测。完整训练方案、逐来源取舍和哈希见 [统一模型记录](unified_model_process.md)。此前单独 Steam 模型文件从当前版本移除，历史结果保留在 Git 提交记录中。

所有历史实验分支的提交已纳入 `main`；GitHub 默认分支和本地工作分支均为 `main`，其余旧分支在确认已合并后删除。1—4 字实验的提交仍可从 Git 历史访问，但当前文件保持统一模型版本。
