# Steam 十万级数据 Spark 处理与单机对照

2026-10-13 使用已清洗的 102,902 条 Steam 简体中文短评。输入哈希与采集报告核对；不重抓、不重新标注，也不改动训练/测试划分。每条数据有游戏 ID、正文、评论时间和“推荐／不推荐”弱标签。

两种实现读取**完全相同的 JSONL 字节**，做相同工作：规范化空白、计算字符数，按游戏、弱标签、UTC 月份和文本长度桶分组，统计每组数量与字符总数。先用评论 ID 的 SHA-256 确定次序，取嵌套的 1 万、5 万、102,902 条输入；准备文件不计时。各方案每档运行 3 次，报告中保存逐次耗时和中位数。Spark 为本机 `local[4]`，不是多机器集群。Spark JVM 启动不计时；两边计时均包括读取 JSONL、解析、清洗与聚合。

| 行数 | Python 中位数 | Spark 中位数 | 聚合核对 |
|---:|---:|---:|---|
| 10,000 | 0.030 秒 | 0.325 秒 | 1,314 组一致 |
| 50,000 | 0.150 秒 | 0.365 秒 | 1,781 组一致 |
| 102,902 | 0.306 秒 | 0.325 秒 | 1,905 组一致 |

全量数据中，空白规范化后平均长度为 41.34 字符；长度不超过 40 字符的有 73,479 条，41—100 字符有 19,306 条，超过 100 字符有 10,117 条。完整的逐游戏／标签、逐月统计、每次耗时、输入哈希和限制见 [`steam_spark_comparison.json`](steam_spark_comparison.json)。**逐月数量不是自然评论热度趋势**：采集时指定了游戏、最近评测筛选、正负分别取样和短文本过滤。

在当前约 10 万条、简单分组统计的场景下，单机 Python 已很快，Spark 没有明显速度优势；1 万条时其调度开销更明显。这正是对规模和工具适用性的实测结论，不能宣称本项目验证了集群加速。操作系统缓存、JVM 预热及顺序运行也会影响数值，不宜把毫秒差距解释为稳定性能差异。

在项目目录、原始清洗文件仍在本机时运行：

```powershell
powershell -ExecutionPolicy Bypass -File .\start_spark.ps1 -Script scripts/benchmark_steam_pipeline.py
```

脚本会重新生成 Git 忽略的 `runtime/steam_benchmark/` 输入副本并覆盖本报告 JSON；无需网络。当前 Windows Spark 仍会提示缺少 `winutils.exe`，但本次 DataFrame 读取和统计已成功完成。
